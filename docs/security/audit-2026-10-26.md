# Security audit — rossmoney.me — 2026-10-26

**Scope:** the `payload-cms` app in this repository and its three live surfaces:

| Surface | Host | Runtime |
| --- | --- | --- |
| Portainer / Nginx Proxy Manager | `https://www.example.com` | container, `SERVER_URL` pinned |
| Vercel production | `https://example.vercel.app` | Vercel, Atlas `rossmoney_me` |
| Vercel preview | `https://dev.example.com` | Vercel, Atlas `example_dev` |

**Method:** code review, `corepack pnpm@10.11.0 audit` (all and `--prod`), and
read-only HTTP/TLS probes of the live sites (GET/HEAD/OPTIONS, header and body
inspection, dependency metadata). No intrusive scanning, credential attacks,
brute force, destructive payloads or live mutations were performed. The only
POSTs to the live surfaces were empty/invalid validation probes that cannot
create a document; a public form submission was not sent to a live site.

The companion policy record is [`csp.md`](./csp.md).

## 1. Findings ranked by real risk to this site

Ranks are about *this* app, not CVSS. "Demonstrated" means the behaviour was
observed on a live or local production surface; "code-confirmed" means the code
path is clear but the live behaviour was not exercised; "observation" means it
is a configuration fact without a demonstrated attack.

### P0 — Next.js `/api/og` is publicly reachable on Vercel and matches a critical `next/og` advisory

**Demonstrated.** On both Vercel surfaces:

```text
GET https://example.vercel.app/api/og?title=Hello&description=World
200 image/png (17–23 KB)

GET https://dev.example.com/api/og?title=Hello&description=World
200 image/png
```

On `www.example.com` the same request is `404 {"message":"Route not found \"/api/og\""}`.

Why it matters: `@payloadcms/next` registers this endpoint with
`runtime = 'nodejs'` and passes `title`, `leader` and — without a length limit —
`description` straight into `ImageResponse` from `next/og`
(`node_modules/@payloadcms/next/dist/routes/rest/og/index.js`). The installed
Next.js is 16.3.3; advisory **GHSA-vcvr-r3jv-pc5j** (critical, RCE in
`next/og` Node `ImageResponse`) affects `>=16.2.0 <16.3.6`. The advisory's
precondition is attacker-controlled values reaching SVG content/attributes/
styles. The endpoint is unauthenticated and takes them from the query string.
Exploitation was **not** attempted; this is a reachable vulnerable code path,
not a proven compromise.

**Action (separate work):** upgrade Next.js to `>=16.3.8`/`16.4.1` as
appropriate, or block `/api/og` at the edge until then. The CSP does not fix
this class of bug; keeping the endpoint on a patched Next is the fix.

### P0/P1 — `@payloadcms/plugin-form-builder` critical advisory; public submissions are creatable

**Demonstrated exposure.** `POST /api/form-submissions` with `{}` returns
`400` validation (“Cannot create this submission because this form does not
exist”), not `403`; the plugin’s default `create: () => true` is in force and the
contact form is public. Anonymous **reads** are blocked (`403`). The installed
plugin is 3.88.0; advisory **GHSA-r488-j9vj-wx3q** (critical, RCE) is fixed in
3.90.0. The public patch for that advisory is an access-control change on form
submission/email reads, so the exact exploit path is not obvious from the diff;
**no RCE was demonstrated**. It is nevertheless a critical dependency finding
on a publicly writable collection.

**Action (separate work):** upgrade Payload and the form-builder plugin to
`>=3.90.0`; consider disabling public form submissions or adding a queue while
that is scheduled.

### P1 — Image optimisation + `sharp` are exposed and conditional on an SVG

**Demonstrated surface.** `/_next/image` is public and processes local media
URLs (`/_next/image?url=%2Fapi%2Fmedia%2Ffile%2F...&w=1920&q=100` returned `200`
on a local production build). Media uploads require authentication, and the
current live media collection contains only three `.docx` files (no SVG).
`next.config.ts` sets `localPatterns`/`remotePatterns` but not
`dangerouslyAllowSVG`, and `sharp` is 0.34.2 (<0.35.5). Advisory
**GHSA-2464-fhr4-w9xw** (critical, image-optimisation RCE when SVG is used)
therefore requires an attacker-controlled SVG to be uploaded first. That is not
anonymous today, but it is one admin upload away.

**Action (separate work):** upgrade `sharp`/Next, and restrict the Media
collection MIME types to the formats the site actually uses.

### P1 — Payload authentication/authorization advisories: mostly not reachable as configured

The audit reports eight critical and several high Payload advisories. The code
review narrows them:

- **First-register RCE (GHSA-97rh-rhh2-7vjv): not reachable.**
  `GET /api/users/init` returns `{"initialized":true}` on all three surfaces;
  the `users` collection already has a user, and Payload’s
  `registerFirstUserOperation` rejects when one exists.
- **Unauthorized update to collection documents (GHSA-f7hx-52q9-hcrf): not
  reachable.** The advisory requires `orderable: true` on a collection or join
  field. `grep -rn orderable src` finds none; no collection uses it.
- **Field access-control bypass on auth collections / token field handling /
  API-key disclosure / polymorphic joins (GHSA-vc4h-q48j-5hcx,
  GHSA-66wr-7vmr-p5jq, GHSA-238x-w2j9-gwwr, GHSA-fpww-c55p-cjv6): not
  demonstrated.** The app has one auth collection (`users`), no API keys and no
  join fields. A compromised admin already has full access; these matter if an
  auth surface is added.
- **Uploaded SVG/XML same-origin JS (GHSA-2pwp-2369-8fg3, GHSA-9qpg-3cf8-w33x):
  requires an authenticated upload.** The current media set has no SVG/XML. The
  CSP is a useful second layer here.

**Action (separate work):** upgrade the Payload packages together to `>=3.90.0`
(Payload, all `@payloadcms/*` plugins and adapters), re-run the integration
suite, and re-check the form-builder/contact flow.

### P1 — Account-lockout denial of service against the single admin

**Code-confirmed.** `Users.auth` does not override Payload defaults:
`maxLoginAttempts: 5`, `lockTime: 600000` (10 minutes). The app adds no
IP-based rate limit around `/api/users/login`; whether the Nginx Proxy Manager
or Vercel edge adds one was not verified (no edge configuration is in this
repository). An unauthenticated attacker can send five bad passwords, lock the
only admin account for ten minutes, and repeat. This was **not** attempted
against the live site because it would lock the real account.

**Action:** put a rate-limit/WAF rule in front of `/api/users/login` (Nginx
Proxy Manager for `www`, Vercel Firewall for the Vercel surfaces), or raise the
lockout cost without making the account unusable.

### P1 — Payload session cookie is not `Secure` by default

**Code-confirmed, not live-demonstrated.** Payload’s `authDefaults` set
`cookies: { sameSite: 'Lax', secure: false }`, and `Users.auth: true` does not
override it. `generatePayloadCookie` passes `secure: collectionAuthConfig.cookies.secure`
straight through. The app sets `sameSite` to Lax (default) and `httpOnly: true`,
but no `secure`. This is true on all three HTTPS surfaces, including the
Portainer one where `SERVER_URL` is pinned.

No login was attempted, so the actual `Set-Cookie` was not observed. HSTS and
SameSite=Lax reduce the practical impact, but a `Secure` cookie is the correct
baseline.

**Action:** set `auth.cookies.secure: true` (or derive it from the request
protocol) on the `Users` collection.

### P2 — HSTS is inconsistent and the `www` preload flag is not eligible

**Demonstrated headers.**

| Surface | `Strict-Transport-Security` |
| --- | --- |
| `www.example.com` (Nginx Proxy Manager) | `max-age=63072000; preload` — **no `includeSubDomains`** |
| `example.vercel.app` | `max-age=63072000; includeSubDomains; preload` |
| `dev.example.com` | `max-age=63072000` |

`preload` requires `includeSubDomains`, so the `www` header cannot be submitted
to the preload list as-is. `dev.example.com` is a subdomain and gets only
`max-age`; that is acceptable for a preview host but different from production.
`http://` requests 301/308 to HTTPS on all three.

**Action:** align the Nginx Proxy Manager HSTS header with Vercel
(`includeSubDomains; preload`) after deciding whether every `*.example.com` host
is HTTPS-only; treat the apex and preview hosts explicitly.

### P2 — `/api/access` discloses the collection/field schema

**Demonstrated.** `GET /api/access` returns `200` and a JSON description of
every collection’s fields and read permissions (6,999 bytes on `www` and the
Vercel surfaces). This is Payload’s normal admin bootstrap endpoint, not a
credential leak, but it tells an attacker the exact field names and the
published-only filter. `/api/users/init` also confirms the collection is
initialised.

**Action:** if the public site does not need it, block `/api/access` and
`/api/users/init` at the edge for anonymous requests, or accept it as low-risk
metadata.

### P2 — `X-Powered-By` advertises the stack

**Demonstrated.** Every surface returns `x-powered-by: Next.js, Payload`.
`poweredByHeader: false` in `next.config.ts` removes the Next.js value; Payload
may still append its own. Low impact, but it is free to remove.

### P3 — Missing cross-origin isolation headers

**Observations.** No `Cross-Origin-Embedder-Policy`,
`Cross-Origin-Resource-Policy` or `Origin-Agent-Cluster` on any surface.
`Cross-Origin-Opener-Policy: same-origin-allow-popups` is present. COEP would
break third-party embeds (reCAPTCHA, Monaco, Vercel analytics) and is not
needed; CORP would reduce media hotlinking; `Origin-Agent-Cluster: ?1` is a
cheap isolation improvement. No demonstrated exploit.

### P3 — `/api` cache headers are `public` on Vercel

**Demonstrated.** `GET /api/pages` on Vercel returns
`cache-control: public, max-age=0, must-revalidate`; on `www` the header is
absent. The content is public, so this is not a leak today, but a `public`
shared-cache directive on a cookie-capable API is the wrong default. Prefer
`private, no-store` for `/api/*` unless a specific endpoint is designed to be
cacheable.

### P3 — Information-disclosure observations

- No source maps are served: a chunk has no `sourceMappingURL`; `<chunk>.js.map`
  is `404`.
- `/.env`, `/.env.local`, `/.git/config`, `/.DS_Store`, `/package.json` and
  `/payload` are `404`.
- `.well-known/security.txt` and `.well-known/change-password` are `404`
  (no security contact policy).
- `robots.txt` names `/admin/*`, `/api/*` and `/payload/*`; that is normal
  hygiene, not a leak.
- The `game-servers` HTML embeds `http://socket-proxy:2375` in page data; an
  internal hostname is exposed in the rendered JSON. It is not reachable from
  the browser, but it is unnecessary detail.
- `/api/cms/site` and `/api/cms/travel` call `assembleSite()`, which uses Payload’s
  local API without `overrideAccess: false`. This bypasses field access for the
  collections it reads, but it only reads `draft: false` documents; a
  `?draft=true` request and a `where[_status]=draft` query both returned
  published-only/zero results. No draft leak was found.

### Not reachable / not a finding

- **GraphQL introspection:** disabled (`__schema` returns “GraphQL
  introspection is not allowed”); a `Users` query returns `403`.
- **`/api/graphql-playground`:** `404`.
- **Media path traversal:** `/api/media/file/..%2f..%2f.env` and the encoded
  variant return `403`.
- **First-register:** `/api/users/init` is `true`; the first-user screen is not
  an open door.
- **`/api/users`, `/api/payload-preferences`, `/api/payload-jobs`,
  `/api/posts`, `/api/categories`, `/api/projects`, `/api/experience`,
  `/api/form-submissions` reads, and all writes to pages/globals/media:** `403`
  for anonymous callers.
- **`use cache` RCE advisory:** the app does not use `use cache`; not reachable.
- **Next image-optimiser SSRF advisory:** the optimiser is reachable, but
  `remotePatterns` only names the configured server host and
  `*.public.blob.vercel-storage.com`, and `localPatterns` only
  `/api/media/file/**`; no arbitrary-host path was demonstrated.

## 4. The `Origin`-dropping proxy, adversarially

`src/proxy.ts` + `src/utilities/adminOrigin.ts` drop the `Origin` request header
only when **all** of these hold:

- the path is `/admin/*` or `/api/*`;
- `Origin` is a parseable absolute URL;
- its normalised origin is **not** already in the static allowlist;
- its host and protocol match the request’s `x-forwarded-host`/`host` and
  `x-forwarded-proto`/Next URL protocol.

Payload’s `extractJWT` then sees no `Origin` and falls back to
`Sec-Fetch-Site`; it accepts `same-origin`, `same-site` or `none`, and rejects
`cross-site` or a missing header when a CSRF allowlist is configured.

Attack cases considered:

- **Cross-origin page, form POST / fetch / `sendBeacon`:** the browser sends the
  attacker’s `Origin` (`https://evil.example`). The proxy sees a host mismatch
  and leaves it; Payload compares it to `config.csrf` and drops the cookie.
- **Cross-origin `<img>` / `<script>` / GET:** `Origin` is absent, but the
  method is GET and Payload does not mutate. The cookie is `SameSite=Lax`, so it
  is not sent on cross-site subresource requests anyway.
- **`Origin: null`** (sandboxed iframe, `data:` URL, redirect): `normaliseOrigin`
  returns `null`; the proxy does not drop; Payload sees `null`, which is not in
  the allowlist, and drops the cookie.
- **Spoofed `X-Forwarded-Host`:** a browser cannot set it on a simple form post;
  a fetch with a custom header would trigger CORS preflight, and the app’s
  `cors` list does not include the attacker. On Nginx Proxy Manager,
  `X-Forwarded-Host` should be overwritten from `$host`; if the edge ever
  forwarded a client-supplied value, the proxy’s host comparison would be the
  weak point. This is a deployment assumption to keep in the Nginx Proxy Manager
  configuration review.
- **`Sec-Fetch-Site: same-site` with no `Origin`:** Payload accepts it. A
  same-site sibling origin (another `*.example.com` host) that omits `Origin`
  on a mutating request could pass; modern browsers include `Origin` on POST,
  so this is a defence-in-depth gap rather than a demonstrated bypass. The
  `SameSite=Lax` cookie is the second layer.

**Conclusion:** no exploitable hole was found in the Origin-dropping logic for
modern browsers. The residual assumptions are (a) a trustworthy
`X-Forwarded-Host` from the Nginx Proxy Manager / Vercel edge and (b) browser
`Origin`/`Sec-Fetch-Site` semantics. Record them in the edge configuration
review.

## 5. Authentication and session behaviour

- **Session cookie:** `payload-token`, `HttpOnly`, `SameSite=Lax`, `Path=/`,
  `Secure` **false** by default (see P1). Code-confirmed from
  `node_modules/payload/dist/collections/config/defaults.js` and
  `dist/auth/cookies.js`.
- **CSRF:** Payload’s `Origin` allowlist plus the proxy fallback (section 4).
  Cross-origin writes keep their `Origin` and are rejected.
- **Login rate limiting:** Payload account lockout only (5 attempts / 10
  minutes), no IP rate limit (P1).
- **First-user setup:** not reachable; `/api/users/init` is `true` on all three
  surfaces. `POST /api/users/first-register` is guarded by the users collection
  lookup, and no successful first-register was attempted.
- **Password reset:** not exercised (it sends mail and is a write). Payload’s
  forgot-password handler returns a generic response; no enumeration was tested.
- **Admin surface:** `/admin` and `/admin/login` return `200` and are cache-
  controlled `private, no-cache, no-store, max-age=0, must-revalidate`.

## 7. CSP before and after

**Before** (all surfaces): `Content-Security-Policy: frame-ancestors 'none';`
— no script, style, connect, image or object policy at all.

**After:** the full public/admin policies in [`csp.md`](./csp.md). They are
enforced on production responses only; `next dev` skips them because HMR needs
`eval` and a WebSocket.

Violations found while bringing the policy up (all on a production build), and
the fixes:

| Surface | Violation | Fix |
| --- | --- | --- |
| `/cv` | `script-src` blocked `eval` from Next’s `util` polyfill pulled in by JSZip via `mammoth/lib/unzip` | use mammoth’s browser bundle + `browser/unzip`; add a `readable-stream` shim via `turbopack.resolveAlias` so the Node `util` polyfill is not bundled |
| `/admin` dashboard | `img-src` blocked `https://www.gravatar.com/avatar/...` | allow Gravatar in the admin policy only |
| `/admin/collections/pages/:id` | `style-src-elem` blocked Monaco’s `editor.main.css` from `cdn.jsdelivr.net` | allow jsDelivr in the admin style/script/font/worker/connect policy only |
| `/contact` submit | `frame-src 'none'` blocked the reCAPTCHA anchor/bframe on `https://www.google.com` | allow the Google reCAPTCHA frame, connect and script sources on public pages only |

After the fixes, the production build produced **zero** `securitypolicyviolation`
events and zero CSP console errors on:

- `/` (home; image present and optimised to 800×420 in the local check),
- `/cv` (DOCX rendered client-side, 6,046 characters of CV text),
- `/contact` (form rendering, plus the full reCAPTCHA script/frame/token flow),
- `/game-servers` (external `archview.example.org` fetch allowed),
- `/admin/login` first paint,
- `/admin` dashboard after login,
- `/admin/collections/pages/:id` edit view (Monaco JSON field),
- a save (autosave `PATCH /api/pages/:id?autosave=true...` → `200`, read-back
  showed the edited title),
- an upload (`POST /api/media` → `201`, media URL returned, cleanup `200`),
- a 404 page.

All `<script>` tags rendered by Next carried the same per-request nonce (17/17
on the home page; a second request had a different nonce). Both Vercel analytics
scripts loaded and both beacons fired (`POST /_vercel/insights/view`,
`POST /_vercel/speed-insights/vitals`) with zero violations.

**One pre-existing issue surfaced but not caused by CSP:** with an absolute
media URL (`serverURL` set, as on the Portainer surface), Next’s image optimiser
returned `400 "url" parameter is not allowed` for
`/_next/image?url=http://localhost:3417/api/media/file/...`. Relative media
URLs (the Vercel behaviour) work. This is a `next.config.ts` `localPatterns`/
`remotePatterns` issue to fix separately; the CSP allows the same-origin
optimiser URL either way.

## 8. What could not be verified

- **Live CSP headers after deployment.** The code was tested on a local
  production build (`next build && next start`); it has not been deployed to
  `www`, Vercel production or the preview.
- **Vercel Blob direct upload.** No `BLOB_READ_WRITE_TOKEN` locally. The policy
  allows `https://*.public.blob.vercel-storage.com` for `img-src` and
  `connect-src`, but the signed-URL PUT was not exercised.
- **A successful contact-form submission end to end.** Google’s test
  reCAPTCHA key loaded the full client flow with zero CSP violations, but the
  server-side verification failed with the test key (expected), so the
  `/api/form-submissions` write did not complete. A live submission was not sent.
- **Live login/session cookies.** No credentials were used; cookie flags are
  code-confirmed, not observed on a live `Set-Cookie`.
- **Password-reset enumeration and delivery.** Not exercised.
- **HSTS preload list status.** Not queried; the `www` header is not eligible
  without `includeSubDomains`.
- **`www` `/api/og` 404 root cause.** Observed on both Vercel surfaces as `200`;
  the Portainer surface returns Payload’s “Route not found”. Likely a
  route-registration difference in the standalone/Node path; not investigated
  further.
- **Dependency upgrade compatibility.** Payload 3.90.0 / Next 16.4.x / sharp
  0.35.x were not installed or tested.

## 9. Recommended follow-ups (separate work, not done here)

1. Upgrade Payload + `@payloadcms/*` + form-builder to `>=3.90.0`.
2. Upgrade Next.js to a version patched for `/api/og` and the image optimiser
   (`>=16.3.8`, ideally `16.4.1`), and `sharp` to `>=0.35.5`.
3. Set `auth.cookies.secure: true` for `Users`.
